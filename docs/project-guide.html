1What Blackbox is

Explain like I’m 5

Blackbox is a practice gym for job interviews. You can talk to a pretend interviewer, join a pretend group discussion with four computer students, and study 500 flashcard-style questions. After every practice, it tells you what you did well, what to study, and how you looked on camera — like a coach who never gets tired.

In tech terms

Blackbox is a full-stack Next.js 16 web application for interview preparation, targeted at five tracks (AI Engineer, ML Engineer, Backend Architect, Full Stack Developer, Data Scientist). It provides LLM-driven mock interviews with adaptive follow-ups and per-answer scoring, a real-time group-discussion simulator with exclusive floor control, a curated 500-question practice bank stored in PostgreSQL, on-device computer vision for delivery metrics (MediaPipe), and browser/AI speech for voice interaction. Every feature degrades gracefully to deterministic offline logic when the AI provider is unavailable.

The main features

Open with the problem, not the tech: “Students prepare for interviews alone, with no feedback. Blackbox simulates the real thing — including group discussions, which nobody can practise alone — and gives measured feedback.” Then mention two technical highlights: the floor-control state machine and the on-device eye-contact measurement.

2The big picture: architecture

Explain like I’m 5

Think of a restaurant. Your browser is the dining table where you sit. The Next.js server is the waiter who takes your order. PostgreSQL is the big notebook in the kitchen where everything is written down so nothing is forgotten. Gemini is a very smart chef in another building that the waiter phones for special dishes. Firebase is the security guard at the door who checks who you are. And the camera magic (MediaPipe) happens right at your table — your picture never goes to the kitchen.

In tech terms
  • Monolithic Next.js app serving both the React UI (App Router, Server and Client Components) and a JSON API (Route Handlers under app/api/*). One deployable unit keeps development simple; boundaries inside the code (lib/db.ts, lib/ai/*, lib/gd/*) keep it modular.
  • Stateless API: every request carries a Firebase ID token; the server verifies it and loads the user from PostgreSQL. No server sessions, so it scales horizontally.
  • Edge middleware (proxy.ts): HTTPS redirect, per-IP rate limiting with separate budgets for AI routes and speech synthesis, and blocking of common probe paths.
  • AI is optional: every AI call has a timeout and a deterministic fallback, so the product works with no API key.
  • Privacy by design: computer vision runs in WebAssembly on the device; only summary percentages are stored.

4How one request travels through the system

Explain like I’m 5

When you press “Submit answer”, your browser writes a letter with your answer and your ID badge. A doorman checks you aren’t sending letters too fast. A guard checks the badge is real. A clerk checks the letter is filled in properly. Then the interviewer reads it, writes it in the notebook, thinks of a reply, and sends a letter back.

In tech terms
  1. Client: lib/api-client.ts attaches Authorization: Bearer <Firebase ID token>, sets a timeout with AbortSignal.timeout, and retries once with a refreshed token on TOKEN_EXPIRED.
  2. Edge: proxy.ts applies a sliding-window rate limit per IP: 120 requests/min for general API traffic, 20/min for AI-generating POSTs, 60/min for speech synthesis.
  3. Authentication: requireUser() verifies the JWT signature, issuer, audience and expiry against Google’s JWKS using jose, then upserts the user row (first request provisions the account).
  4. Validation: parseBody(req, schema, maxBytes) enforces a body size limit (413) and the zod schema (422 with field details).
  5. Business logic in lib/ai/* and data access only through lib/db.ts.
  6. Errors: known ApiErrors map to status codes; anything unexpected becomes a generic 500 and is logged with a request ID that is also returned to the client.

5The database: PostgreSQL + Prisma

Explain like I’m 5

A database is a set of super-organised notebooks. One notebook lists every user. Another lists every interview, and each interview page says which user it belongs to. When you delete your account, every page with your name is torn out too, so nothing is left behind.

In tech terms
  • Schema-first: prisma/schema.prisma defines models and enums (TargetRole, ExperienceLevel, PracticeCategory, Difficulty, InterviewMode, SessionStatus, PracticeStatus, ChatRole). @@map gives snake_case table and column names.
  • Migrations: versioned SQL in prisma/migrations (init, then practice_key_points which added a TEXT[] column). Applied with prisma migrate deploy.
  • Postgres features used: enum types, array columns (role_targets, tags, key_points), a GIN index on role_targets so “questions for my track” (has / isEmpty) is fast, JSONB for transcripts and reports, a unique constraint on (user_id, question_id) for progress upserts.
  • Optimistic concurrency: interview turns are appended with updateMany where { id, updatedAt: expected }. If two submits race, only one write matches the old timestamp; the other gets a 409 instead of corrupting the transcript.
  • Seeding: prisma/seed.ts upserts the 500 questions by slug in batches of 25, so it is idempotent (safe to run on every deploy).
  • Connection: one Prisma client singleton with the PrismaPg adapter (connection pooling via pg).

Why JSON columns for transcripts?

A transcript is always read and written as a whole and its shape evolves (turn kinds, key points, refined flags were added later). Storing it as JSONB avoids a join per turn and avoids migrations for every new field, while the fields we filter and aggregate on (score, status, role, dates) stay as proper typed columns.

6Sign-in and security

Explain like I’m 5

Google gives you a special sticker after you log in. Every time you ask Blackbox for something, you show the sticker. Blackbox checks the sticker with Google’s official stamp pad to make sure it isn’t fake or old. It also only lets you open your own notebook pages, never someone else’s.

In tech terms
  • Firebase Auth on the client (Google, GitHub OAuth; phone OTP with reCAPTCHA). The client obtains a short-lived ID token (a signed JWT, ~1 hour).
  • Server verification with jose.jwtVerify against securetoken@system.gserviceaccount.com JWKS: checks RS256 signature, iss, aud (project ID) and expiry. Keys are cached.
  • Authorization: every query is scoped by the user ID, e.g. getOwnedInterview(userId, id) — you can’t read another user’s session even with its ID (prevents IDOR).
  • Demo mode for local development: a dev:<id> token accepted only when DEV_AUTH_BYPASS=true and not in production.
  • Hardening: security headers (CSP, HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy, COOP/CORP), rate limits, body size limits, strict zod validation, generic 500 messages, no secrets in code (env vars), the Gemini key sent in a header (not the URL) so it never appears in logs.
  • Privacy: account deletion (DELETE /api/me) removes the user and, via cascades, all their data. Video is processed on-device; recorded answer audio (only with Gemini on) is transcribed in memory and never stored.

7The AI layer: Gemini, fallbacks and prompts

Explain like I’m 5

Blackbox has a very clever helper (Gemini) it can phone. But phones sometimes don’t connect. So Blackbox also keeps a big book of good questions and rules for scoring, and if the phone call fails, it uses the book. You still get a full interview — just a bit less magical.

In tech terms
  • REST client (lib/ai/gemini.ts): generateText and generateJson call generativelanguage.googleapis.com/v1beta/models/{model}:generateContent with the key in the x-goog-api-key header.
  • Resilience: hard timeout per call; one retry on 429/5xx; on 404 (retired model) it falls through a GEMINI_MODELS list and remembers the model that worked; “thinking” is kept low for latency.
  • Structured output: JSON mode plus a zod schema validates every AI reply; malformed JSON is treated as “AI unavailable”, so the fallback runs.
  • Graceful degradation: every feature catches AIUnavailableError and uses deterministic logic: practice-bank questions, a heuristic rubric, topic packs for GD, generic project questions.
  • Extra capabilities: synthesizeSpeech() (Gemini TTS models, prebuilt voices like Charon, Kore, Puck; PCM wrapped into WAV) and transcribeAudio() (16 kHz WAV sent inline for accurate transcripts).
  • Prompt design: system prompt sets persona, company style, track focus, level and mode; rules demand plain spoken English (no markdown), one question per turn, and JSON with a fixed schema. Server-side guards still enforce rules the model might ignore (e.g. follow-up limits, on-topic check in GD).
Interview tip

“What if the LLM is down or returns garbage?” — Every call has a timeout, the JSON is schema-validated, and each feature has an offline path that produces a complete, coherent session. The health endpoint reports ai: "configured" | "fallback" and the UI labels heuristic scores honestly.

8The mock interview and the adaptive interviewer

Explain like I’m 5

The interviewer doesn’t just read a list. It listens. If you say “I don’t know”, it gives you a few hints and lets you try again, like a kind teacher. If you talk about something you built, it gets curious and asks about it. If your answer is short, it nudges you to say more. At the end, it tells you exactly which ideas to study for next time.

The flow of one interview

  1. Setup: choose company style (Google, Amazon, Microsoft, Meta, AI lab, startup, consulting), mode (Coached, Standard, Bar raiser), experience level and voice.
  2. Preflight: camera check, accent selection for dictation, AI voice availability.
  3. Opening: the interviewer greets you and asks you to introduce yourself.
  4. Loop: the interviewer speaks → you answer (voice or typing) → the server reads your answer and decides the next move → repeat. 5 main questions, plus up to 2 follow-ups and coaching retries.
  5. Finish: the evaluation report with scores, strengths, improvements, a practice plan and an answer-by-answer review with key points to study.

How the interviewer decides what to say next

In tech terms
  • Answer signals (lib/ai/answer-signals.ts): regular expressions detect “don’t know”, help requests, project stories and nervousness; a dictionary of ~28 technologies (RAG, vector DBs, LoRA, Kafka, Redis, Kubernetes, React, SQL…) maps each to a realistic follow-up question and study points. Unit-tested.
  • Allowed moves are computed on the server: coaching only once per question; follow-ups only after a project story, max 2, never twice in a row; main questions until 5. The model chooses within those moves (JSON: kind, reaction, question, keyPoints), and the server overrides anything not allowed.
  • Personalisation: experience level maps to difficulty (Entry/Junior → Easy/Medium, Mid → Medium/Hard, Senior/Staff → Hard); the profile’s preferred topics are asked first; tone follows the mode and the candidate’s energy.
  • Turn model: each interviewer turn stores content (what was said), prompt (the bare question), kind (question / followup / coaching), keyPoints and ref (practice-bank ID).
  • Idempotency: the client sends the interviewer-turn number with every answer. A duplicate or late submit for an old turn gets 409 NOT_YOUR_TURN, and optimistic concurrency stops two answers being written at once.
  • Scoring without AI (heuristic rubric): 30 + length×30 + structure×15 + impact×15 + ownership×10 − filler penalty, clamped 15–92. Length is best at 90–260 words; structure counts signposts (“first”, “because”, “trade-off”); impact counts numbers and outcome verbs; ownership counts “I built / I decided”. “Don’t know” answers are capped at 12 and marked Not attempted.
  • Overall score = technical depth 30% + problem solving 25% + communication 20% + structure 15% + composure 10%.

9Speech: listening and talking

Explain like I’m 5

Your browser has ears and a mouth. The ears write down what you say while you speak. We tell the ears your accent (like “English, India”) so they understand you better. The mouth reads questions aloud; we pick the nicest-sounding voice and make it pause between sentences like a real person. If Blackbox has its Gemini key, an even better mouth and a second, more careful pair of ears are used.

Listening (speech-to-text)

In tech terms
  • Web Speech API SpeechRecognition with continuous = true and interimResults = true: interim words stream into the answer box as you speak; final words replace them.
  • Accent: rec.lang is the candidate’s accent (en-IN, en-US, en-GB…), defaulting to the browser locale — a major accuracy improvement for Indian English.
  • Restarts: browsers end a session after silence or ~60 s; the recognizer commits what it heard and restarts immediately in onend, so long answers aren’t cut off.
  • Accurate transcript (with Gemini): while you answer, AnswerRecorder captures microphone audio with the Web Audio API, downsamples to 16 kHz mono WAV in the browser, and on submit sends it to /api/transcribe. Gemini transcribes it, given your accent and the question for spelling technical terms. The refined text replaces the live text and is flagged refined.
  • Browser note: Chrome streams words live; Edge returns words only after pauses — the UI tells Edge users.

Talking (text-to-speech)

In tech terms
  • Voice ranking voiceQuality(): neural voices (names containing “Natural/Online/Neural/Premium”) score highest, then Google voices; legacy Windows SAPI voices (David, Zira) score lowest; the user’s accent region gets a bonus.
  • Natural delivery: text is split into sentences (very long ones at a comma), each spoken as its own utterance with a slightly varied rate (±3%) and a pause of ~260–500 ms between sentences (longer after questions). This removes the “machine reading a book” effect and avoids Chrome cutting off long utterances.
  • Distinct speakers: in the GD room each panelist gets a different voice (picked without repeats) plus its own pitch/pace.
  • Gemini voices (when configured): /api/tts returns natural speech from Gemini’s TTS models with a delivery style, e.g. “warmly and conversationally”. Falls back to the browser voice on any error.
  • Captions: the sentence being spoken is shown on screen with a blur-in animation.

10Eye contact and posture: real measurements

Explain like I’m 5

A tiny camera brain on your computer finds 478 dots on your face and dots on your shoulders, about 7 times every second. It checks: is your head facing the screen, and are your eyes looking at it? Are your shoulders level and is your head not sinking down? It adds up the seconds you did it right. If you looked at the screen for 3 minutes out of 4, your eye contact is 75%. Nothing is guessed, and your video never leaves your computer.

In tech terms

Eye contact

  • Head pose: from MediaPipe’s 4×4 facial transformation matrix (column-major), yaw = asin(−r₂₀) and pitch = atan2(r₂₁, r₂₂).
  • Gaze: the blendshapes eyeLookIn/Out/Up/Down (0–1) tell whether the eyes are turned away; above 0.55 counts as looking away.
  • Calibration: the first ~14 steady frames (~2 s) set the candidate’s own baseline yaw/pitch, because webcams sit at different heights. Afterwards a frame counts as eye contact when |yaw − base| ≤ 16°, |pitch − base| ≤ 14° and gaze isn’t away.
  • Blinks (both eyeBlink > 0.6) keep the previous state, so blinking isn’t penalised.
  • Score = seconds of eye contact ÷ seconds of camera analysis. Leaving the frame counts against you; face presence is reported separately.

Posture

  • Pose Landmarker gives nose (0) and shoulders (11, 12) with visibility scores; frames only count when both shoulders are visible (> 0.5).
  • Scale-free features: shoulder width; neck ratio = (shoulder mid-height − nose height) ÷ shoulder width; shoulder tilt angle.
  • After calibrating a baseline, a frame is not upright if tilt > 7° (uneven shoulders), neck ratio < 78% of baseline (slouching / head sinking) or shoulder width > 130% of baseline (hunched too close).
  • Score = upright seconds ÷ seconds shoulders were visible; reported only with ≥ 10 s of visible shoulders, otherwise “Not measured”.

Honesty rules

  • Time is accumulated per processed frame (capped at 0.5 s per frame so a frozen tab doesn’t inflate numbers).
  • Metrics are sent only if at least 15 s of camera time was analysed; the results page shows exactly how they were measured (e.g. “looking at the screen for 2m 31s of 3m 14s”).
  • MediaPipe’s harmless “INFO: Created TensorFlow Lite XNNPACK delegate” console lines are filtered so they don’t appear as errors.

11The group discussion room: floor control, the queue and AI speakers

Explain like I’m 5

Imagine a talking stick. Only the person holding the stick may talk. The teacher (moderator) holds it first and asks a question, then puts the stick on the table — now anyone may reach for it. Whoever reaches first gets it, and everybody else must wait in a line. Nobody can shout over the person holding the stick. When they finish, the stick goes to the next person in line. That is exactly how Blackbox’s GD room works.

In tech terms

FloorController — the lock

  • A pure TypeScript state machine (no timers, no I/O): IDLE → MODERATOR → OPEN ⇄ LOCKED → CLOSED.
  • One exclusive lock. In OPEN, request(id) appends to a FIFO queue; in LOCKED/MODERATOR, requests are rejected with a reason (locked, not-open…), so nobody can interrupt.
  • Lock tokens: every grant increments a token. release(token) only works for the current holder’s token — a slow AI reply arriving late can never release or speak under a lock it no longer owns (prevents race conditions).
  • Exposes an immutable snapshot with subscribe/getSnapshot, used by React’s useSyncExternalStore for tear-free rendering.

DiscussionConductor — the orchestration

  • Runs the session on top of the lock: moderator intro → opens the floor → collects requests during a 1.4 s bidding window → grants the first requester → hand-off to the next queued participant after a 0.7 s gap.
  • AI bidding: each agent has an eagerness (0.45–0.75); agents bid after a random 0.9–3.1 s delay, so the human has a fair chance to grab the floor first.
  • Moderator: a follow-up question every 4 turns; nudges after 7 s of silence; closes after 10 turns.
  • Watchdogs: a user turn is capped at 120 s and an AI turn at 45 s; every async step uses an AbortController so leaving the room cancels everything cleanly.
  • All I/O (model calls, speech, timers, randomness) is injected, so the whole flow is unit-tested deterministically with Vitest fake timers.

12Practice Hub, dashboard, project review and the coach

Practice Hub — 500 questions

Explain like I’m 5

It’s a library of 500 interview flashcards in 10 shelves: LLMs, ML, MLOps, System Design, DSA, Backend, Frontend, Analytics, Behavioural, Communication. Each card shows the key points, a great answer, a weak answer, why it matters and a tip. You mark cards as “reviewed” or “confident”, and the app remembers.

In tech terms
  • Questions live in PostgreSQL (seeded from TypeScript files under prisma/seed-data; a check script verifies 50 per category, no duplicate slugs or texts, 3–4 key points each).
  • GET /api/practice: filtered by the user’s track with roleTargets has role OR isEmpty (GIN index), by category, difficulty and search; cursor pagination; facet counts; per-user progress joined in.
  • Progress is an upsert on the unique (user, question) pair; an AI grader reviews a typed attempt; the per-question coach chat (/api/chat) is persisted in coach_messages.

Dashboard and track

  • Readiness index = weighted average of available signals: interview average (50%), practice coverage of your track’s core areas (30%; “confident” counts fully, “reviewed” 60%), group-discussion average (20%). Missing signals are left out and the weights renormalised.
  • Track: chosen at onboarding and switchable anytime from the dashboard header; it is saved to your profile and reshapes the question mix, interview focus, competencies, module order and recommendations.

Project review

Paste or upload a project write-up; the server asks Gemini for 3–8 tailored questions (or uses six proven generic ones offline), then reviews each of your answers. Text extraction from uploaded files happens in the browser.

13Testing, quality and running the project

Quality gates
  • npm run typecheck — TypeScript strict mode
  • npm run lint — ESLint incl. React hooks rules
  • npm test — Vitest: floor control, conductor, answer signals
  • npm run build — production build of every route
  • npx tsx scripts/check-question-bank.ts — bank integrity
Run it locally
  1. Open the folder in VS Code.
  2. Terminal: cd frontend
  3. npm install (first time)
  4. npm run dev:local
  5. Open http://localhost:3000 → demo account.

Add GEMINI_API_KEY in frontend/.env.local for AI voices, accurate transcripts and model grading.

Deploying to production

  1. Provision PostgreSQL (e.g. Neon, Supabase, RDS) and set DATABASE_URL.
  2. Set Firebase variables, GEMINI_API_KEY, NEXT_PUBLIC_SITE_URL; add the domain to Firebase authorised domains.
  3. Release step: npm run db:deploy && npm run db:seed; then npm run build && npm start (or Vercel).
  4. Point uptime checks at /api/health. Use a shared store (e.g. Redis) for rate limits if running several instances.

14Interview question bank about this project

Short, confident answers you can give when someone asks about Blackbox.

Q1. Give me a two-minute overview of your project.

Blackbox is an interview-preparation platform for engineers. It has an adaptive AI mock interviewer, a group-discussion simulator with four AI candidates and strict turn-taking, a 500-question practice bank, and on-device webcam analysis for eye contact and posture. It’s a Next.js 16 app with a PostgreSQL database through Prisma, Firebase sign-in verified on the server, and Google Gemini for AI — with deterministic fallbacks so it works even without the AI. The parts I’m proudest of are the floor-control state machine for discussions and making the delivery metrics genuinely measured rather than estimated.

Q2. How does the group discussion stop people from interrupting each other?

A finite state machine with a single exclusive lock. When someone holds the floor the state is LOCKED and every other request is rejected; when the floor is OPEN, requests join a FIFO queue and are granted one at a time with a short hand-off gap. Each grant has an increasing token, and only the current token can release the lock, so a late AI response can’t steal or release the floor.

Q3. How do you queue participants, and is it fair to the human?

Requests made during a short bidding window after the floor opens are queued in arrival order. AI agents bid after a random 0.9–3.1 second delay weighted by their eagerness, so a human who speaks up promptly usually gets the floor first, like in a real GD.

Q4. How do multiple AI speakers stay distinct and on topic?

Each agent has a persona (analytical, pragmatic, contrarian, synthesizer), its own voice, pitch and pace, and its own Gemini voice when available. The prompt forces plain, short, on-topic replies that react to the previous speaker; a server-side check rejects off-topic replies. Offline, lines are built from hand-written topic packs of pro, con and middle-ground points.

Q5. How do you calculate eye contact? Isn’t it just a dummy number?

No, it’s measured. MediaPipe’s face landmarker runs in the browser about seven times a second. Each frame I compute head yaw and pitch from the face transformation matrix and check the eye-gaze blendshapes, compared to a baseline calibrated in the first two seconds. Eye contact is the seconds looking at the screen divided by the seconds analysed. Posture works the same way with shoulder tilt, neck height relative to shoulder width, and distance. Video never leaves the device.

Q6. What happens if Gemini is down or you have no API key?

Every AI call has a timeout and schema validation, and every feature catches the failure and uses deterministic logic: questions from the practice bank filtered by track and level, a transparent heuristic rubric, topic packs for discussions, and generic project questions. The UI labels heuristic scores honestly.

Q7. How does the interviewer adapt to the candidate?

After each answer the server reads signals — “don’t know”, help requests, project mentions with specific technologies, nervousness. Then it chooses from allowed moves: coach with hints and allow one retry, ask a follow-up about the project’s technology, or acknowledge specifically and move on. Difficulty follows experience level and the profile’s focus areas come first. The model chooses within those rules and the server enforces them.

Q8. Why PostgreSQL and not MongoDB?

The data is relational: users own sessions, progress links users and questions, and I need constraints, transactions and cascading deletes. Postgres also gives JSONB for transcripts, arrays and GIN indexes for track filtering — so I get document flexibility where I need it without giving up relational guarantees.

Q9. How do you prevent duplicate answer submissions?

Two layers. The client sends the interviewer-turn number it is answering; a mismatched number returns 409. And writes use optimistic concurrency: the update only applies if the row’s updated-at timestamp is unchanged, so two concurrent submits can’t both be written.

Q10. How is authentication secured?

Firebase handles sign-in; the client sends the ID token on every request; the server verifies the JWT’s RS256 signature, issuer, audience and expiry with Google’s public keys using jose. Every query is scoped to the user’s ID, so even guessing another session’s ID returns 404.

Q11. How did you make speech recognition more accurate?

Three things: setting the recognizer to the candidate’s accent such as en-IN, restarting immediately when the browser ends a session so words aren’t lost, and — when Gemini is configured — recording the answer as 16 kHz WAV in the browser and getting an accurate server transcription that also knows the question, so technical terms are spelled correctly.

Q12. Why does the AI voice sound more natural?

I rank voices by quality, preferring neural voices, and speak sentence by sentence with small varied pauses and slight rate variation instead of one flat utterance. With Gemini, I use its TTS voices with a speaking style prompt.

Q13. How is the readiness index calculated?

A weighted average of the signals that exist: interview average 50%, practice coverage of the track’s core areas 30%, group-discussion average 20%; missing signals are excluded and weights renormalised, so new users aren’t penalised for features they haven’t tried.

Q14. How do you protect the API from abuse and cost spikes?

Per-IP rate limits in the edge proxy with a stricter budget for AI routes, body-size limits, strict validation, and timeouts on model calls. The Gemini key is only used server-side and sent in a header.

Q15. How did you test timing-heavy code like the discussion room?

The conductor receives all its dependencies — model calls, speech, clock, randomness — through injection, so tests drive it with Vitest fake timers and fake agents and assert exact sequences: who gets the floor, that interruptions are rejected, hand-offs, and the transcript at the end.

Q16. What would you improve next?

A shared rate-limit store for multi-instance deploys, real-time multiplayer GD with WebSockets so real candidates can join, server-side streaming of model replies to cut perceived latency, and analytics on which questions candidates struggle with to personalise practice.

Q17. How do you handle user privacy?

Video analysis runs on-device and only percentages are stored; recorded answer audio is transcribed in memory and not stored; users can delete their account and all data in one action thanks to cascading foreign keys; and the privacy page documents exactly which processors are used.

Q18. Why Next.js instead of a separate frontend and backend?

One codebase and one deployment, shared TypeScript types and zod schemas between client and server, server rendering for a fast landing page, and route handlers that are enough for this API. It’s a modular monolith that could be split later.
